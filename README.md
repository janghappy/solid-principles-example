# SOLID 원칙 실습

SOLID 다섯 원칙을 간단한 예제 코드로 실습하는 프로젝트입니다.
원칙마다 원칙을 어긴 코드(`bad`)와 지킨 코드(`good`)를 나란히 두어 비교할 수 있게 했습니다.

| 패키지 | 원칙 | 예제 |
|---|---|---|
| `solid.srp` | 단일 책임 원칙 | 면적 계산 / 단위 변환 분리 |
| `solid.ocp` | 개방-폐쇄 원칙 | 도형 추가 시 `AreaCalculator` 수정 여부 |
| `solid.lsp` | 리스코프 치환 원칙 | 무료 회원의 토너먼트 주최 |

## SOLID란?

로버트 C. 마틴(Uncle Bob)이 정리한 객체지향 설계 원칙 다섯 가지의 앞 글자를 딴 이름입니다.
목표는 **변경에 강한 코드**입니다. 요구사항은 계속 바뀌므로, 무언가 바뀔 때 고쳐야 하는 범위를 최소화하고 기존 코드를 깨뜨리지 않고 기능을 추가할 수 있게 만드는 것이 핵심입니다.

SOLID를 지키지 않은 코드에서 흔히 나타나는 증상은 다음과 같습니다.

- **경직성(Rigidity)**: 작은 변경 하나가 여러 클래스의 연쇄 수정을 부른다.
- **취약성(Fragility)**: 한 곳을 고쳤는데 관련 없어 보이는 다른 곳이 깨진다.
- **부동성(Immobility)**: 다른 곳에 재사용하고 싶어도 얽힌 의존성 때문에 떼어낼 수 없다.

---

## S — 단일 책임 원칙 (Single Responsibility Principle)

> 클래스는 단 하나의 변경 이유만 가져야 한다.

"하나의 일만 한다"보다 **"하나의 액터(변경을 요구하는 주체)에게만 책임진다"**로 이해하는 편이 정확합니다.
면적 계산 규칙을 바꾸자는 요구와 지원 단위를 늘리자는 요구는 서로 다른 이유로 발생하므로, 한 클래스에 있으면 서로의 변경에 휘말립니다.

- **위반 예**: `bad.RectangleAreaCalculator`가 면적 계산과 단위 변환을 모두 수행
- **해결**: 계산(`RectangleAreaCalculator`)과 변환(`AreaConverter`)을 분리
- **위반 신호**: 클래스 이름에 `And`/`Manager`/`Util`이 붙음, 서로 관련 없는 필드·메서드 묶음, 한 클래스가 지나치게 많은 import를 가짐
- **주의**: 책임을 지나치게 잘게 쪼개면 클래스 수만 늘고 흐름을 따라가기 어려워집니다. "실제로 따로 바뀌는가"를 기준으로 판단합니다.

## O — 개방-폐쇄 원칙 (Open-Closed Principle)

> 소프트웨어 요소는 확장에는 열려 있고, 수정에는 닫혀 있어야 한다.

새 기능을 추가할 때 **기존 코드를 고치는 대신 새 코드를 추가**하는 구조를 만들라는 뜻입니다. 이미 테스트·배포된 코드를 건드리지 않으므로 회귀 버그 위험이 줄어듭니다.

- **위반 예**: `bad.AreaCalculator`가 `instanceof`로 도형을 분기 → 도형이 늘 때마다 수정 필요
- **해결**: `Shape.area()`로 면적 계산 책임을 각 도형에 위임. `good.Triangle`은 계산기를 수정하지 않고 추가됨
- **위반 신호**: 타입이나 enum 값에 따른 `if-else`/`switch`가 여러 곳에 반복됨
- **도구**: 다형성, 전략(Strategy) 패턴, 템플릿 메서드 패턴, 플러그인 구조

## L — 리스코프 치환 원칙 (Liskov Substitution Principle)

> 상위 타입의 객체를 하위 타입의 객체로 치환해도 프로그램의 정확성이 깨지지 않아야 한다.

상속은 코드 재사용이 아니라 **행위의 약속(계약)을 물려받는 것**입니다. 하위 타입은 다음을 지켜야 합니다.

- 사전조건을 **강화하지 않는다** (부모보다 더 까다로운 입력을 요구하지 않음)
- 사후조건을 **약화하지 않는다** (부모가 보장한 결과를 똑같이 보장)
- 부모가 던지지 않는 새로운 예외를 던지지 않는다

- **위반 예**: `bad.FreeMember.organizeTournament()`가 `UnsupportedOperationException`을 던짐 → `Member` 자리에 넣을 수 없음
- **해결**: 능력별 인터페이스(`TournamentJoiner`, `TournamentOrganizer`)로 분리하고, 각 회원이 할 수 있는 일만 구현
- **위반 신호**: 빈 오버라이드, `UnsupportedOperationException`, 호출부의 `instanceof` 분기
- **고전 사례**: `Square extends Rectangle` — 정사각형은 수학적으로 직사각형이지만, `setWidth()`가 높이까지 바꾸면 직사각형의 계약이 깨집니다. "is-a"가 성립해도 **행위가 치환 가능한지**를 따져야 합니다.
